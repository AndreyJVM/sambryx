    Тестирование

    Браузерные smoke-тесты проверяют собранный React-интерфейс Sambryx. Они запускают локальный Java HTTP-сервер и подменяют API на границе HTTP. Нужен JDK 21; Docker, учётные записи сервера и настоящие SSH/Samba/AD-соединения для этого набора не нужны.

    Выбор проверок

    Проверяйте затронутую область: backend, frontend, браузер, Docker image или полный Compose. Для новой логики нужен тест наблюдаемого поведения и значимого отказа; документация проверяется сборкой, ссылками и рендером. Команды backend/frontend — в разработке. Набор CI выбирается по изменённым путям; правила — в README репозитория и руководстве по поставке.

    Backend-отчёт Allure

    Для корневого JUnit 5 набора нужен JDK 21. Docker, Node.js и глобальная установка Allure для обычных backend-тестов не требуются. Из корня проекта:

    export JAVA_HOME=/usr/lib/jvm/java-21-openjdk-amd64
export PATH="$JAVA_HOME/bin:$PATH"
# Remove results from previous runs before collecting a new report.
rm -rf target/allure-results target/site/allure-maven-plugin
./mvnw -Dfrontend.skip=true test
./mvnw -B allure:report
python3 -m http.server 8000 --bind 127.0.0.1 --directory target/site/allure-maven-plugin

    Откройте локальный отчёт и остановите сервер через Ctrl+C. При падении тестов команду allure:report можно выполнить отдельно: она читает уже записанные результаты и не запускает тесты повторно. Отчёт не заменяет код выхода Maven. Не используйте clean между тестами и генерацией: он удалит результаты.

    В pom.xml закреплены адаптер allure-junit5 2.29.1, Maven plugin 2.15.2 и Java CLI Allure Report 2.32.0. Maven загружает их при первом использовании; CLI устанавливается в target/allure/ только при генерации отчёта. AspectJ и отдельный Node.js runtime не нужны. Исходные результаты находятся в target/allure-results/, HTML — в target/site/allure-maven-plugin/. Каталоги генерируются и игнорируются Git. Результаты накапливаются между запусками, поэтому перед новым набором удаляйте их, как показано выше.

    Основная навигация — Behaviors: @Epic задаёт область (например, Configuration and backups), @Feature — предмет и границу проверки: unit с mock commands, HTTP с реальной security chain, HTTP без фильтров или local shell component. Используем одну настраиваемую иерархию Epic → Feature; Suites и Packages оставляем техническим представлением Java-классов. Не добавляем параллельную иерархию suite labels.

    @DisplayName описывает конкретный проверяемый результат на английском. Во всех корневых backend-сценариях заданы читаемые заголовки, включая Monitoring/readiness, AD, parser, shell command construction и общие configuration/HTTP error tests. Существующие заголовки Compliance сохранены. Для @ParameterizedTest(name = "{0}") используем короткий case label через JUnit Named/MethodSource, если исходный аргумент — конфигурация, credential, большой вывод, пустое значение или неоднозначный boolean. Короткие безопасные значения (например, failed stage, timeout или форма Samba boolean) можно показывать непосредственно с именем параметра. Адаптер 2.29.1 добавляет имя сценария перед именем invocation: повторять {displayName} в pattern не нужно. Не заменяем различающиеся cases одним общим заголовком и не меняем assertions ради оформления.

    Удаление account в unit/HTTP проверках подтверждается составом и порядком mock-команд без рекурсивного удаления; сохранность реальных файлов эти проверки не доказывают. Share directory local shell cases отдельно проверяют временные файлы, mode и owner.

    Mock SSH/JSch проверяет работу с подменённой границей, а не реальное SSH/Samba/AD окружение. Local shell использует временные файлы и указанные в feature stub utilities; это не проверка production sudo policy или установленного Samba. Literal backup comparison сравнивает текст, не раскрывает include и не подтверждает семантическую эквивалентность Samba-конфигураций. Число invocations показывает размер запущенного набора, а не процент покрытия.

    Существующая CI-job Backend Checks после тестов, включая отказ, генерирует HTML, если есть *-result.json. Артефакты backend-allure-results и backend-allure-report доступны семь дней. При отсутствии результатов генерация и загрузка пропускаются; ошибка тестового шага сохраняется. Raw results загружаются и при ошибке генерации HTML. Для просмотра скачайте и полностью распакуйте backend-allure-report, затем выполните в каталоге с index.html:

    python3 -m http.server 8000 --bind 127.0.0.1

    Откройте тот же локальный адрес. Открытие index.html через file:// может блокировать загрузку данных браузером. Отчёт не публикуется в Pages или сторонних сервисах; history/trends между CI-запусками не сохраняются.

    Захват stdout/stderr JUnit Platform явно отключён в src/test/resources/junit-platform.properties: адаптер умеет прикладывать эти потоки из report entries. Интеграция не подключает сбор Spring/SSH logs, конфигурации, ключей, запросов, ответов или переменных окружения. В отчёт входят имена тестов, статусы, метаданные и сообщения/stack traces ошибок; используйте синтетические данные в тестах и не добавляйте секреты в assertions, параметры, display names или явные report entries/attachments. Frontend, browser, отдельные smoke Maven-проекты и real SSH suite (BackupSshIT) в корневой запуск test не включены.

    API оформления: Allure JUnit reference, исходники адаптера 2.29.1, JUnit named arguments.

    Версии и команды: JUnit 5 adapter, Maven plugin 2.x, Allure Report 2.

    Первый запуск

    Нужны JDK 21, Node.js 20+ и npm. Node.js используется для сборки приложения, браузерные сценарии написаны на Java/JUnit с Playwright. Из корня проекта:

    cd frontend
npm ci
npm test
npm run lint
npm run build
cd ..
./mvnw -B -f tools/browser/pom.xml exec:java \
  -Dexec.mainClass=com.microsoft.playwright.CLI -Dexec.classpathScope=test \
  "-Dexec.args=install chromium"
./mvnw -B -f tools/browser/pom.xml verify

    На минимальном Linux вместо install chromium используйте install --with-deps chromium. Установка системных библиотек может потребовать административные права; в CI она выполняется на одноразовом runner. Версия Playwright закреплена в tools/browser/pom.xml. После её изменения установите соответствующий Chromium снова.

    Из frontend/ доступны обёртки npm run test:browser:install и npm run test:browser. Вторая сначала собирает UI, затем запускает Java-тесты. Сборка приложения и Spring-контекст в самом тестовом Maven-проекте не запускаются.

    Собранный frontend/dist обслуживается только на 127.0.0.1 со случайным свободным портом. Чужой preview-сервер не используется. Нет npm-зависимости от @playwright/test. Для локальной диагностики допустим PLAYWRIGHT_CHANNEL=chrome перед командой Maven; этот выбор нужно указать в отчёте, поскольку системный Chrome отличается от закреплённого Chromium.

    Что проверяется

    Набор tools/browser/src/test/java/sambryx/browser/ запускается в Chromium в четырёх конфигурациях:

    Конфигурация Размер Тема
    desktop-light 1440 × 1000 Светлая
    desktop-dark 1440 × 1000 Тёмная
    mobile-light 320 × 844 Светлая
    mobile-dark 320 × 844 Тёмная

    Проверки охватывают парольный вход и вход с ключом, bootstrap CSRF-токена, предупреждение о смене SSH-ключа, навигацию, сохранение темы, поиск ресурсов, пустые результаты, ошибки загрузки и устаревшие данные, вложенные диалоги, отмену опасных действий и блокировку кнопок управления при недоступных данных Dashboard.

    Сценарии ConfigurationBackupIT проверяют выбранный файл и последствия в подтверждении, Cancel/Escape без mutation, pending без повторной отправки и конфликтующего сохранения, успех с перечитыванием формы и списка копий, ошибку перечитывания после успешного restore, отказ проверки, ошибку restart и потерю ответа. Снимки подтверждения, pending и результата сохраняются в frontend/test-results/ для каждой темы и размера экрана.

    Текущий restore API не различает отказ testparm и сбой последующих команд структурированным кодом: оба возвращают HTTP 500. Поэтому интерфейс сообщает, что восстановление не подтверждено, скрывает серверные детали и предлагает проверить конфигурацию и службу перед повтором. Это сообщение не обещает сохранность действующего файла при неизвестной ошибке. Успешный restore и неудачное последующее перечитывание отображаются отдельно.

    API-фикстуры используют только синтетические реквизиты и адреса. Незаданные API-запросы, неожиданные мутации, внешние обращения и необработанные ошибки JavaScript завершают проверку ошибкой. Новый endpoint нужно добавить в фикстуру явно; не заменяйте неизвестные ответы универсальным успешным результатом.

    Эти тесты не подтверждают серверную защиту CSRF, корректность проверки SSH-ключа библиотекой, работу настоящего Samba/AD или совместимость с Astra. Для этого сохраняются backend integration tests и отдельная Production Compose Smoke с реальными TLS/SSH/SMB.

    Выборочная проверка и диагностика

    После сборки можно запустить только одну группу, например backup/restore:

    ./mvnw -B -f tools/browser/pom.xml verify '-Dit.test=ConfigurationBackupIT,BackupCreationIT'

    JUnit-классы WorkspaceIT, AdministratorSessionIT, ConfigurationBackupIT, BackupCreationIT и ShareAccessIT содержат обычные параметризованные тесты с вариантами из BrowserVariant. Каждый тест получает отдельный browser context; общий BrowserTestRuntime отвечает только за запуск, диагностику и освобождение ресурсов. Только проверка логотипов: -Dit.test=BrandingIT. Полный набор ограничен таймаутом JVM в пять минут; автоматических retry нет. Используйте ожидания Playwright по состоянию интерфейса вместо sleep.

    JUnit-результаты сохраняются в tools/browser/target/failsafe-reports/. Screenshots и failure traces находятся в tools/browser/target/browser-artifacts/. Открыть конкретный trace из корня проекта:

    ./mvnw -B -f tools/browser/pom.xml exec:java \
  -Dexec.mainClass=com.microsoft.playwright.CLI -Dexec.classpathScope=test \
  "-Dexec.args=show-trace tools/browser/target/browser-artifacts/CASE/trace.zip"

    Замените CASE именем каталога неудачного сценария. Отчёты не входят в Git. CI-job Browser Smoke Tests прикладывает JUnit-результаты, screenshots и traces в артефакте browser-smoke-report на семь дней. Логотипы проверяются отдельно в job Branding Assets; для этого не требуется Node.js или сборка frontend.

    Добавляя сценарий, проверяйте наблюдаемый результат и необходимые побочные эффекты. Предпочитайте доступные роли и подписи элементов. При изменении поведения сначала добавьте регрессионный тест, который воспроизводит проблему, затем изменяйте реализацию.

    Восстановление конфигурации через Docker + SSH

    Production Compose Smoke выполняет публичные backup/restore-запросы через HTTPS и настоящий SSH. Успех подтверждается сравнением байтов smb.conf, чтением API и SMB; отказ повреждённой копии — сохранностью действующего файла и PID smbd, а также чтением SMB после ошибки. Этот тест запускается в CI в существующем job Production Compose Smoke и использует только одноразовый Compose-проект.

    ConfigWorkflowIntegrationTest отдельно проверяет HTTP error mapping и отсутствие команд замены/restart при ошибке testparm; граница SSH там замокана, security filters отключены. Проверка настоящих filters, TLS, CSRF и host-key verification сохраняется в Compose smoke. Эти уровни не подтверждают восстановление пользователей, паролей, SID или всех данных из томов.

    Коллизии имён резервных копий

    BackupCollisionTest фиксирует время на границе форматирования даты и выполняет команды реального сервиса над временными файлами. Подменены только SSH executor, sudo, testparm и systemctl; Bash, cp, mktemp, ln и NUL-safe retention выполняются локально. Тесты подтверждают сохранность нескольких снимков в одну секунду, выбранной restore-копии, восстановление имени с суффиксом и остановку без замены/restart при отказе создания safety copy. Отдельно проверяются повторные совпадения, исчерпание имён, частичная запись, отказ публикации, каталоги, висячие ссылки и пути с пробелами/кавычками.

    Первое имя сохраняет формат smb.conf.backup_yyyyMMdd_HHmmss; при совпадении используются суффиксы _1–_99. После 100 занятых имён операция завершается ошибкой. Готовое содержимое публикуется hard link из скрытого временного файла в том же каталоге; существующая запись не заменяется. Временный файл имеет права 0600 и удаляется при штатном выходе команды. Нужны Bash, GNU-совместимый ln -T, поддержка hard link файловой системой и разрешение существующей SSH-учётной записи выполнять команду через sudo bash; проект не меняет sudoers. При отсутствии этих возможностей создание завершается ошибкой до restore/update. Лимит retention остаётся равным 10; старые имена поддерживаются.

    Эти проверки не доказывают общую конкурентность, атомарность restore, rollback, устойчивость к аварийному завершению хоста или защиту от изменения каталога другим привилегированным процессом. Compose smoke проверяет новую команду через настоящий SSH, но не фиксирует время и не гарантирует воспроизведение коллизии; детерминированные коллизии покрывает файловый тест.

    Аудит зависимостей frontend

    Проверка #28 от 25 октября 2026 года воспроизводится из frontend/:

    npm ci
npm audit
npm audit --omit=dev
npm ls vite esbuild tailwindcss postcss-nested postcss-selector-parser react-router-dom react-router

    Audit зависит от актуальной базы advisory: сохранённый lockfile фиксирует версии, но не будущий результат аудита. Ненулевой код выхода означает наличие findings; не скрывайте его в CI. --omit=dev помогает отделить runtime-зависимости, но сам по себе не доказывает применимость.

    Исходный lockfile на 0bb8456 давал 7 findings: 6 moderate и 1 high. Выбран ограниченный переход Vite 5.4.21 → 6.4.5 с esbuild 0.25.12. Vite 6 поддерживает существующий Node.js 20.15.0, а установленный React plugin 4.7.0 поддерживает Vite 6. Требования Node.js, React, Tailwind, маршрутизация, конфигурация сборки и Docker-поставка сохраняются. Используемые настройки не затрагивают изменения SSR, Sass, resolve conditions и экспериментальных API из руководства миграции Vite 5 → 6.

    Пакеты исходного отчёта Применимость и решение
    Vite (high) Dev-server: обход ограничений файловой системы, обработка source maps и launch-editor; часть advisory относится к Windows, часть — и к другим ОС. Обновлён до 6.4.5, выше всех затронутых диапазонов исходного отчёта. В runtime Docker находятся JRE и JAR со статическими ресурсами, Vite туда не включается.
    esbuild (moderate) GHSA-67mh-4wv8-2f99: доступ стороннего сайта к esbuild dev-server. Sambryx использует esbuild через Vite при сборке; зависимость обновляется вместе с Vite до исправленной версии 0.25.12.
    postcss-selector-parser, postcss-nested, tailwindcss (3 moderate) GHSA-rj75-hqrm-r3gf: CPU exhaustion при разборе недоверенных CSS-селекторов. Это одна первичная уязвимость и два зависимых package findings. Парсер 6.1.4 остаётся в build tooling Tailwind 3.4.19/postcss-nested 6.2.0; вход — доверенные исходники репозитория, HTTP-запросы и пользовательские CSS сервером не компилируются. Сборка непроверенных PR всё равно исполняет недоверенный код и должна оставаться изолированной без секретов.
    react-router, react-router-dom (2 moderate) Поставляются в JS bundle, остаются 6.30.6. GHSA-wrjc-x8rr-h8h6 требует передачи контролируемого атакующим пути в Link/useNavigate. В Layout, DashboardPage и ActiveDirectoryPage назначения заданы константами; GlobalSearch строит назначения /shares, /users, /groups, а не берёт их из результатов API. GHSA-337j-9hxr-rhxg касается SSR hydration: здесь BrowserRouter/Routes и createRoot, без SSR и deserializeErrors.

    После обновления получены 5 moderate, 0 high в полном audit и 2 moderate в --omit=dev. Это зарегистрированные остаточные findings, а не исправления Router или CSS parser. Решение ограничено текущими путями данных: не передавайте внешние URL, query-параметры или значения API в Link/useNavigate и не добавляйте серверную компиляцию пользовательского CSS без повторной оценки. При появлении SSR, динамических назначений навигации, недоверенных CSS или новых advisory пересмотрите исключения до публикации изменения. Повторяйте audit при обновлении lockfile.

    Исправления этих остаточных advisory доступны в Router >=7.18.0 и parser >=7.1.6. Переход Router 6 → 7 и Tailwind 3 → 4 либо принудительная замена parser за пределами диапазона postcss-nested — отдельные изменения совместимости; в #28 они не выполняются. Не используйте npm audit fix --force и не отключайте проверки ради нулевого отчёта.

    Срок действия сессии

    Контракт сессий проверяют AdministratorSessionIntegrationTest с настоящими security filters и подменённой SSH-границей, а также ExecutionSessionManagerTest. Управляемый Clock позволяет проверить границы 15 минут и пяти минут ожидания без sleep. Реальный сервис restore продолжает цепочку команд после отзыва доступа; отдельная проверка подтверждает отказ новому запросу и отсутствие повторного disconnect.

    session.spec.mjs проверяет предупреждение, явное продление, отказ просроченному продлению, возвращение из сна, несколько вкладок и отсутствие продления автоматическим переходом. Для предупреждения сохраняются снимки RU/EN на desktop/mobile в обеих темах. Фикстуры браузера не доказывают серверный deadline; mock SSH не доказывает завершение настоящего удалённого процесса. Эти границы проверяются разными уровнями тестирования.

    Проверки механизма выпуска

    Для изменений CI/release в облаке применяется полный план, включая настоящий стандартный Docker image и Production Compose Smoke. Локально достаточно затронутых guards и быстрых checks. Release coordinator проверяется отдельно без внешней публикации.

    Утилиты CI сгруппированы по назначению:

    • scripts/ci/checks/ — выбор проверок и верификация документации, JAR и Docker Hub.
    • scripts/ci/release/ — последовательная публикация новой версии и выбор JAR.
    • tools/smoke/ — отдельные Java/JUnit-проверки Docker image и Production Compose, без Spring-контекста и сборки приложения.
    • scripts/ci/tests/ — все Python-тесты утилит, отдельно от исполняемых скриптов.

    Полный набор запускается из корня репозитория без установки Python-пакета проекта:

    python3 -B -m unittest discover -s scripts/ci/tests -p 'test_*.py' -v

    Для отдельных проверок release:

    python3 -B -m unittest discover -s scripts/ci/tests -p 'test_release*.py' -v

    Проверяются порядок публикации, отказы внешних операций, запрет перезаписи версий, registry errors, CodeQL exact source SHA, dependency cancellation/skips и SHA-256 JAR. Внешние команды и HTTP подменены; это не настоящий выпуск и не проверка GitHub concurrency scheduler. Порядок выпуска и ручное восстановление описывают действия после сбоя.

    Java Docker image smoke

    Нужен JDK 21. Быстрые тесты не используют Docker:

    ./mvnw -B -f tools/smoke/pom.xml test

    Реальный image проверяется отдельно, без пересборки приложения:

    ./mvnw -B -f tools/smoke/pom.xml -Pdocker-smoke verify \
  -Dsmoke.image=sambryx:local "-Dsmoke.jar=$(realpath target/sambryx-0.0.1-SNAPSHOT.jar)"

    Укажите уже собранный образ и соответствующий JAR. Проверяются non-root UID, идентичность JAR, точные байты UI/assets, remote mode и HTTP 401 для анонимного запроса. Контейнер запускается с read-only filesystem и временным /tmp, порт публикуется только на loopback. Проверка удаляет только свой контейнер при успехе и отказе; принудительное завершение JVM через SIGKILL не позволяет выполнить cleanup. Обычный backend test эти проверки не запускает.

    JUnit-тесты вспомогательной логики используют временные JAR, настоящий локальный HTTP-сервер и подменённую Docker CLI-границу. Профиль docker-smoke проверяет настоящий Docker image, но не устанавливает SSH-соединение и не проверяет SMB: это остаётся задачей Production Compose Smoke.

    Java Production Compose smoke

    После подготовки образов из инструкции развёртывания:

    ./mvnw -B -f tools/smoke/pom.xml -Pproduction-smoke verify \
  -Dsmoke.image=sambryx-ci:production

    Профили docker-smoke и production-smoke запускайте отдельно. Второму не нужен smoke.jar. Он использует настоящий nginx, SSH, Samba и SMB-клиент в отдельном Compose-проекте: проверяет доверие TLS, SSH host identity, вход по ключу, CSRF и secure/HttpOnly cookie, сохранность UID, host keys, пароля, shares и SMB-файла после пересоздания. Проверяются успешный backup/restore и отказ testparm для повреждённой копии без изменения активного конфига, PID Samba и доступности SMB. В конце тот же созданный через API синтетический пользователь удаляется через аутентифицированный DELETE /api/users/sgfixture с CSRF и настоящим SSH-выполнением. Независимые проверки через Docker exec подтверждают отсутствие записи в Linux (getent passwd, exit 2) и Samba (успешный pdbedit -L), а также сохранность home, файла в home, синтетического /var/mail/sgfixture, каталога ресурса и записанного через SMB файла. До удаления фиксируются содержимое файлов, числовые UID/GID, режимы и типы; после удаления они должны совпасть. Проверки состояния выполняются даже при ошибочном HTTP-статусе или success=false. Данные рабочих серверов не используются.

    Это характеристика уже реализованного удаления без userdel -r; production-логика не меняется. Узел — standalone Ubuntu 24.04 из deploy/production/samba, с настоящими Linux/Samba account utilities и SSH. Его systemctl — ограниченный адаптер к Supervisor, поэтому smoke не доказывает работу systemd на полноценном сервере, других дистрибутивов или AD. Mail-файл создаётся синтетически: доставка почты и работа MTA не проверяются. Отсутствие учётной записи проверяется напрямую, без нового SMB-входа после удаления; сохранённые UID/GID могут остаться без имён. Корневой sandbox runner для этой проверки не используется.

    Compose запускается с --env-file /dev/null, уникальным project name и случайными loopback-портами. Cleanup удаляет только volumes и контейнеры этого проекта. Приватные ключи создаются во временном каталоге, SMB-реквизиты передаются через stdin во временный файл с правами 600. Нет Python-кода внутри тестового Samba-контейнера. Application logs и реквизиты в отчёт не включаются. SIGKILL и авария Docker-хоста могут помешать очистке; оставшийся тестовый проект нужно проверить отдельно перед удалением.

    Быстрые JUnit-тесты проверяют HTTP/CSRF, передачу stdin и изоляцию проекта. Они не подтверждают настоящий SSH/SMB: это делает только явно запущенный production-smoke. Пять проверок rendered Compose model находятся в ComposeModelIT и входят в production-smoke. Отдельно, без запуска контейнеров:

    ./mvnw -B -f tools/smoke/pom.xml -Pproduction-smoke verify -Dit.test=ComposeModelIT

    Ограниченный отчёт готовности сервера

    ServerReadinessServiceTest подменяет только CommandExecutor: проверяет успешные read-only вызовы без заявления полной готовности, отказы команд, отсутствие exit status и остановку после транспортного сбоя. Проверяются отсутствие чувствительного вывода и ограниченный набор команд. ServerReadinessIntegrationTest использует настоящий сервис и security filters с подменённым SshSessionManager: проверяются HTTP 401 и отчёт после успешного SSH-входа при отказе удалённых проверок.

    JAVA_HOME=/usr/lib/jvm/java-21-openjdk-amd64 ./mvnw -B -Dfrontend.skip=true \
  -Dtest=ServerReadinessServiceTest,ServerReadinessIntegrationTest test
npm --prefix frontend run build
JAVA_HOME=/usr/lib/jvm/java-21-openjdk-amd64 ./mvnw -B -f tools/browser/pom.xml \
  verify -Dit.test=ServerReadinessIT

    Браузерные JUnit/Playwright-сценарии подменяют HTTP API: проверяют отказ проверки после входа, следующее действие, недоступный/повреждённый отчёт, очистку старого результата и отсутствие изменений на сервере. Проверены ожидание и защита от двойного запуска; успешные проверки чтения сохраняют частичный статус. RU/EN-отчёты сохраняются в browser-artifacts на desktop/mobile в обеих темах. Mock SSH/API не доказывает работу настоящего Samba, sudoers или SMB. Рабочие серверы и реальные секреты для этих тестов не используются. Границы отчёта описаны в настройке сервера.

    Backup через непривилегированную SSH-сессию

    BackupSshIT запускается явно и входит в Production Compose Smoke job после сборки Samba-образа. Он создаёт собственный контейнер и синтетического пользователя admin, получает доверенный host key через Docker-консоль и подключается настоящим SSH с новым ключом. Root-shell через sudo запрещён. Проверяются создание и чтение списка копий, сохранность предыдущей копии и конфигурации, отказ копирования и очистка временного файла.

    docker build -t sambryx-samba-node:ubuntu24.04 deploy/production/samba
./mvnw -B test -Dfrontend.skip=true -Dtest=BackupSshIT \
  -Dbackup.ssh.image=sambryx-samba-node:ubuntu24.04

    Sudoers формируется настоящим scripts/setup-samba-server.sh внутри одноразового контейнера. Вызовы установки пакетов в тесте подменены: проверяется создание policy, а не доступность репозиториев ОС. SSH, sudo и файловые команды не подменяются. Тест не меняет работающий Sandbox, не проверяет полную production sudo policy, восстановление или веб-интерфейс. Локальные shell-тесты BackupCollisionTest отдельно проверяют коллизии одного timestamp, ошибки утилит, исчерпание имён, символические ссылки и отказ очистки после публикации.

    Достоверность статуса AD

    GET /api/ad/status возвращает nullable boolean для isJoined, dnsReachable, kerberosWorking и winbindWorking: true означает подтверждённый успех, false — подтверждённый отрицательный результат, null — отсутствие достоверного результата. Текущая реализация подтверждает только членство: команда net ads testjoin должна завершиться с кодом 0 и вывести отдельную строку Join is OK. Другой успешный вывод даёт isJoined: null. Ненулевой выход или ошибка SSH дают ошибку API, а не isJoined: false. Достоверное отсутствие членства текущая команда не классифицирует.

    DNS, Kerberos и служба Winbind не проверяются и возвращают null; имя домена также возвращается как null. UI показывает «Не проверено» / «Not checked», не выводит UNKNOWN как имя домена и убирает предыдущий статус при ошибке обновления. Успешный join/leave сохраняет существующую последовательность команд с последующим чтением статуса; ошибка этого чтения не отменяет уже выполненную операцию.

    AdDiagnosticsIntegrationTest проверяет реальный сервис, HTTP-сериализацию и SSH executor, подменяя только JSch Session/Channel. HTTP security filters в этом компонентном тесте не подключены; они проверяются отдельными тестами безопасности и сессий. AdStatusIT проверяет RU/EN в Chromium с подменой HTTP-ответов, включая null, подтверждённые значения и ошибку обновления. Эти тесты не подтверждают реальную совместимость с AD; доменное окружение и реальные проверки остаются в #64.

    Изоляция staging при сохранении

    ConfigStagingTest запускает настоящий Bash и файловые утилиты над временным каталогом. SSH executor, sudo, testparm и systemctl подменены; FIFO-барьеры без sleep удерживают две операции на validation и проверяют независимые файлы и устанавливаемый контент. Проверяются planted symlink, mode, ошибки mktemp/write/validation/metadata/move, cleanup failure, отсутствие чужого удаления и restart после отказа. SambaConfigServiceTest проверяет порядок backup/install/restart; ConfigWorkflowIntegrationTest — API с настоящим сервисом и parser, но mocked SSH и отключёнными security filters.

    BackupSshIT дополнительно проверяет сохранение через настоящий SSH непривилегированного пользователя с setup-generated sudoers, настоящим testparm и root-owned каталогом. В одноразовом Docker-стенде systemctl заменён маркером: реальный restart Samba не проверяется. Проверяются успешная установка, owner/mode, отказ validation, запрет sudo tee/mv, отсутствие утечки staging и отсутствие restart при отказе. Пересечение двух SSH-сохранений удерживается FIFO-барьерами вокруг настоящего testparm; проверяются разные root-owned файлы, установка собственного контента и независимая очистка. Запуск: JAVA_HOME=/path/to/jdk21 ./mvnw -Dfrontend.skip=true -Dtest=BackupSshIT -Dbackup.ssh.image=<prepared-local-image> test.

    Штатная поставка sandbox и сохранение через приложение

    SandboxConfigSaveIT запускает корневой Compose с изолированными именами контейнеров, собственными volumes, случайными паролем и портами, собирая node из штатного Dockerfile. После настоящего SSH-входа admin проверяется сохранение описания через HTTP API, метаданные, точный валидный backup, настоящий restart smbd и отказ настоящего testparm без изменения active config/PID. Проверяются отсутствие staging, отказ privileged shell, понятная ошибка несовместимых sudo permissions до backup и восстановление packaged policy при restart node без изменения config. Здесь нет mocks testparm/systemctl/SSH. Браузерные клики не выполняются: проверяется тот же HTTP endpoint, который вызывает UI.

    JAVA_HOME=/path/to/jdk21 ./mvnw -f tools/smoke/pom.xml \
  -Dtest=SandboxConfigSaveIT -Dsmoke.root="$PWD" \
  -Dsmoke.image=sambryx-save-review:local test

    Образ приложения предварительно собирается из проверяемого JAR через основной Dockerfile. Для проблем DNS только внутри build-сети Linux Docker можно передать тесту -Dsmoke.build.network=host; это касается установки пакетов в build, не runtime-изоляции. Для проверки опубликованного node без локальной сборки передайте -Dsmoke.node.image=andreyvorobevaqa/samba-node-sandbox. Предварительно загрузите этот образ через docker pull. Тест очищает только собственный Compose project и volumes. Рабочие контейнеры не меняются.
