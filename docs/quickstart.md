# Быстрый старт

Основной сценарий: один администратор подключает уже работающий Samba-сервер по SSH.
Панель устанавливается из готового Docker-образа, Nginx предоставляет HTTPS.

## Что подготовить

- Машину с Docker Engine, Docker Compose и Git для получения файлов поставки.
- DNS-имя панели и TLS-сертификат с полной цепочкой и приватным ключом. Браузер должен
  доверять сертификату; имя в URL должно входить в сертификат.
- SSH-адрес и порт Samba-сервера, доступные **из контейнера панели**, и SSH-реквизиты
  администратора по [инструкции подготовки сервера](server-setup.md).
- Публичный SSH-ключ сервера и SHA-256 отпечаток, сверенные через независимый доверенный
  административный канал по [инструкции доверия](ssh-host-keys.md).

JDK, Maven и npm на машине установки не нужны. Установка панели не устанавливает Samba
на удалённом сервере и не меняет его SSH-настройки.

## Установка и первое подключение

1. Получите файлы поставки и подготовьте `.env`, TLS и `known_hosts` по разделу
   [настройки production Compose](production.md#setup). Выберите конкретный
   опубликованный тег образа или digest вместо `latest`.
2. Запустите [панель для существующего сервера](production.md#existing-server)
   и проверьте готовность контейнеров. По умолчанию HTTPS слушает только Docker-хост
   на `127.0.0.1:8443`; доступ с другой машины требует явно выбранного адреса и разрешённого
   сетевого доступа, описанных там же.
3. Откройте HTTPS-адрес панели с `/ui/`. В форме «Подключение к серверу» укажите SSH-хост,
   порт (кнопка «Порт: 22»), пользователя и пароль либо содержимое приватного ключа.
   Это реквизиты Linux/SSH, а не пароль Samba/SMB и не новая учётная запись панели.
   Для ключа используйте поддерживаемый формой ключ без passphrase и защитите его на машине оператора.
4. Нажмите «Подключиться». Успешный вход открывает панель с обзором сервера. Проверьте
   статус Samba и раздел общих папок; пустой список допустим, если ресурсы ещё не созданы.
   Создание первого ресурса выполняйте только после проверки, что подключён нужный сервер.

Адрес браузера и SSH-хост различаются: `localhost` в форме означает контейнер панели,
а не компьютер с браузером. Таблица адресов и разбор отказов находятся в
[production-инструкции](production.md#first-connection).
Неизвестный или изменённый ключ блокирует вход; не принимайте показанный отпечаток без
независимого подтверждения.

Если отдельного Samba-сервера ещё нет, используйте дополнительный
[полный стек с Samba](production.md#bundled-samba).
Для разработки из исходников см. [сборку и поставки](distribution.md) и
[Docker Sandbox](https://github.com/AndreyJVM/sambryx/blob/master/docker/README.md).

## После первого подключения

- Создайте локальных [пользователя и группу](users-groups.md), если нужных записей ещё нет.
- Настройте [отдельный ресурс](shares.md) и ознакомьтесь с изменениями прав при сохранении.
- Проверьте [доступ с SMB-клиента](permissions.md) для разрешённого и постороннего пользователя.
- Перед изменением конфигурации убедитесь, что есть [нужные резервные копии](configuration-backups.md).

## Первый частный ресурс: контрольный проход

Пример для локальных Linux/Samba-учётных записей: один новый пользователь, отдельный
пустой каталог и именованный доступ без гостя. Не применяйте его к существующим данным.
Это не проверка AD или всех вариантов ACL.

1. На **Обзоре** запустите [проверку готовности](server-setup.md#server-readiness).
   Разберите каждый отказ до изменений. Даже успешные проверки чтения оставляют
   административные операции «Не проверены»: они не подтверждают запись или SMB-доступ.
2. Убедитесь, что Linux-логин `sgtrial` свободен. В **Пользователях** создайте его
   с уникальным временным паролем. Сохраните пароль безопасно:
   он будет установлен и для Linux, и для Samba. Не используйте пароль SSH-администратора.
3. В форме ресурса откройте **Обзор** и перейдите в `/srv/samba`. Родитель должен
   уже существовать; вся его физическая цепочка до `/` должна принадлежать root
   без записи для группы и остальных. Нажмите **Новая папка**, введите `sgtrial`,
   включите **Подготовить личную папку (0700)** и явно укажите локального владельца
   `sgtrial` и его локальную группу. Нажмите **Сохранить**, проверьте путь,
   владельца, группу и режим, затем подтвердите создание. Выберите новую папку.
   Подробные требования и поведение при частичном отказе описаны в
   [руководстве подготовки личной папки](private-directory.md).

   Для версии без этого UI или при отдельной административной подготовке доступен
   server-side fallback через доверенный SSH-сеанс на **Samba-сервере**. Если путь
   уже существует, остановитесь и выберите другой: не меняйте владельца существующих
   данных ради этого примера.

   ```bash
   id sgtrial
   # The parent must already exist; stop on failure and inspect partial state.
   sudo -n mkdir -m 0700 -- /srv/samba/sgtrial &&
     sudo -n chmod 00700 -- /srv/samba/sgtrial &&
     sudo -n chown -- "sgtrial:$(id -gn sgtrial)" /srv/samba/sgtrial
   namei -l /srv/samba/sgtrial
   ```

   Все родительские каталоги должны разрешать пользователю проход (`x`). Если это
   не так, согласуйте отдельный тестовый путь с администратором вместо изменения
   прав общих родителей. Сохранение ресурса само по себе не назначает права или
   владельца: UI-подготовка и SSH fallback — отдельные административные действия.
4. В **Общих папках** создайте ресурс `sgtrial` с путём `/srv/samba/sgtrial`:
   «Только чтение» выключено, гостевой доступ выключен, разрешённые пользователи —
   `sgtrial`, маска файлов — `0600`, каталогов — `0700`. Оставьте `force user`,
   `force group` и `write list` пустыми. Сохраните и убедитесь, что Samba работает.
5. На отдельной Linux-машине клиента установите `smbclient` (Ubuntu:
   `sudo apt install smbclient`). Подставьте доступный **клиенту** адрес Samba-сервера
   вместо `files.example.org`. Это не HTTPS-адрес панели и не внутреннее Docker-имя.
   Команда запросит Samba-пароль интерактивно; не добавляйте его в аргументы.

   ```bash
   umask 077
   trial_dir=$(mktemp -d)
   printf 'SMB onboarding probe\n' > "$trial_dir/source.txt"
   smbclient //files.example.org/sgtrial -U sgtrial \
     -c "put $trial_dir/source.txt onboarding-probe.txt; get onboarding-probe.txt $trial_dir/download.txt; ls"
   cmp "$trial_dir/source.txt" "$trial_dir/download.txt"
   ```

   Успех: файл загружен и скачан, `cmp` завершился с кодом `0`. Одного открытия
   панели, списка ресурсов или успешного `testparm` недостаточно. Для нестандартного
   опубликованного SMB-порта добавьте `-p <порт>` к `smbclient`.
6. Проверьте новое подключение с другой действующей Samba-учётной записью, которой
   нет в `valid users`: `smbclient //files.example.org/sgtrial -U otheruser -c ls`.
   Ожидается отказ открытия ресурса. Неверный пароль постороннего пользователя
   проверяет аутентификацию, а не ограничение ресурса.
7. Удалите только тестовый файл через разрешённую SMB-сессию и локальные копии:

   ```bash
   smbclient //files.example.org/sgtrial -U sgtrial -c 'del onboarding-probe.txt'
   rm -- "$trial_dir/source.txt" "$trial_dir/download.txt"
   rmdir -- "$trial_dir"
   ```

При отказе проверьте адрес и порт SMB с клиента, затем пароль Samba, `valid users`
и права пути по [руководству диагностики](permissions.md). Не исправляйте отказ
выдачей `sudo ALL`, отключением SSH/TLS-проверок или `chmod -R 777`.
После проверки решите, нужен ли тестовый ресурс дальше. Удаление ресурса в панели
не удаляет каталог; удаление пользователя не удаляет его данные.

Обновление установленной панели и границы возврата предыдущей версии описаны в
[инструкции обновления и ограниченного отката](production.md#web-update).
